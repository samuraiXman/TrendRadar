## 2. 主要模块详细分析

### 2.1 爬虫核心模块 (main.py)

**文件路径**：`main.py`  
**代码行数**：~4,921 行  
**职责**：数据爬取、处理、推送的核心业务逻辑  

#### 模块结构

```python
main.py
├── 配置加载 (load_config)
│   └─ 从 config.yaml 和环境变量读取配置
├── 数据抓取 (fetch_news)
│   └─ 调用 newsnow API 获取多平台数据
├── 数据处理 (process_news)
│   ├─ 数据归一化
│   ├─ 去重
│   └─ 本地存储
├── 关键词过滤 (filter_by_keywords)
│   ├─ 普通词匹配 (or 逻辑)
│   ├─ 必须词验证 (+ 前缀，and 逻辑)
│   ├─ 过滤词排除 (! 前缀)
│   └─ 数量限制 (@ 前缀)
├── 权重计算 (calculate_weight)
│   ├─ 排名权重 (60%)
│   ├─ 频次权重 (30%)
│   └─ 热度权重 (10%)
├── 排序 (sort_news)
│   └─ 按权重和配置优先级排序
├── 推送模式处理
│   ├─ daily: 推送当日所有新闻
│   ├─ current: 推送当前榜单新闻
│   └─ incremental: 推送新增新闻
├── 多渠道推送 (send_notifications)
│   ├─ 企业微信 (wework)
│   ├─ 飞书 (feishu)
│   ├─ 钉钉 (dingtalk)
│   ├─ Telegram
│   ├─ 邮件 (email)
│   ├─ ntfy
│   ├─ Bark
│   └─ Slack
└── 主程序入口 (main)
    └─ 按配置定时或单次执行
```

#### 关键函数

| 函数名 | 行数 | 职责 |
|--------|------|------|
| `load_config()` | ~100 | 加载配置文件和环境变量 |
| `check_version_update()` | ~30 | 检查新版本 |
| `fetch_news_from_api()` | ~50 | 调用 newsnow API |
| `save_news_to_file()` | ~40 | 保存新闻到本地文件 |
| `filter_by_keywords()` | ~150 | 关键词过滤逻辑 |
| `calculate_weight()` | ~60 | 权重计算 |
| `run_crawler()` | ~200 | 单次爬虫执行 |
| `send_feishu_notification()` | ~80 | 飞书推送 |
| `send_wework_notification()` | ~100 | 企业微信推送 |
| `send_dingtalk_notification()` | ~90 | 钉钉推送 |
| `send_telegram_notification()` | ~60 | Telegram 推送 |
| `send_email_notification()` | ~120 | 邮件推送 |

#### 数据流示例

```
# 单次爬虫执行流程
run_crawler()
  ├─ 1. fetch_news_from_api() 
  │     └─ 调用 newsnow API 获取原始数据
  │
  ├─ 2. save_news_to_file()
  │     └─ 保存到 output/2025年11月15日/txt/HH时MM分.txt
  │
  ├─ 3. 读取 frequency_words.txt
  │     └─ 解析关键词配置（分组管理）
  │
  ├─ 4. filter_by_keywords()
  │     ├─ 逐条新闻进行过滤
  │     └─ 返回匹配的新闻集合
  │
  ├─ 5. calculate_weight()
  │     ├─ 计算每条新闻的权重分数
  │     └─ 返回带权重的新闻列表
  │
  ├─ 6. 按推送模式选择
  │     ├─ daily: 推送今天所有（去重前推送过的）
  │     ├─ current: 推送当前时刻的
  │     └─ incremental: 推送首次出现的
  │
  └─ 7. send_notifications()
        ├─ 构建消息体
        ├─ 消息分批处理
        └─ 并行推送到多个渠道
```

#### 技术债务

| 债务项 | 描述 | 影响 |
|-------|------|------|
| 单文件巨型 | 4921 行代码混合多个职责 | 难以测试、维护、扩展 |
| 无单元测试 | 缺少功能单元测试 | 修改易破坏现有功能 |
| 同步 I/O | 使用 requests 同步请求 | 推送延迟、无法高并发 |
| 硬编码字符串 | 错误消息等硬编码 | 国际化困难 |
| 没有日志系统 | 仅有 print 输出 | 生产环境调试困难 |
| 递归嵌套深 | 关键词过滤逻辑嵌套多层 | 可读性差、易出 bug |

#### 子模块结构

##### 2.2.1 数据查询工具 (tools/data_query.py)

**实现类**：`DataQueryTools`  
**工具数量**：4 个

```python
class DataQueryTools:
    async def get_latest_news(platforms, limit) → List[Dict]
        # 获取最新一批爬取的新闻数据
        # 入参：platforms(平台列表) limit(返回条数)
        # 返回：[{title, platform, rank, timestamp, ...}]
        # 缓存：15分钟 TTL
    
    async def get_news_by_date(date, platforms, limit) → List[Dict]
        # 获取指定日期的新闻
        # 入参：date(YYYY-MM-DD) platforms(平台) limit(条数)
        # 返回：该日期的新闻列表
        # 关键：支持多天查询
    
    async def get_trending_topics(date, limit) → List[Dict]
        # 获取热点话题榜单
        # 入参：date(日期) limit(返回条数)
        # 返回：按热度排序的话题列表
        # 计算：基于权重算法
    
    async def search_news(keyword, platforms, date_range) → List[Dict]
        # 搜索包含关键词的新闻
        # 入参：keyword(搜索词) platforms limit date_range
        # 返回：匹配的新闻列表
        # 方式：全文搜索(contains)
```

#### frequency_words.txt 语法

```
# 示例关键词配置文件

# 第1组：AI 相关
AI
ChatGPT
人工智能
+技术                    # 必须词
!广告                    # 过滤词
@10                      # 数量限制

# 第2组：股市相关（用空行分隔）
A股
上证

+涨跌
```

**解析规则**：
- 空行分隔不同词组
- `+` 前缀表示必须词（AND 关系）
- `!` 前缀表示过滤词（排除）
- `@` 前缀表示数量限制
- 其他词为普通词（OR 关系）

#### Dockerfile 分析

```dockerfile
# 基础镜像
FROM python:3.10-slim

# 安装 supercronic (Linux cron replacement)
# 支持 ARM64 和 AMD64 架构

# 复制依赖
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 复制应用文件
COPY main.py .
COPY docker/manage.py .

# 执行脚本转换（CRLF → LF）
COPY docker/entrypoint.sh /entrypoint.sh
RUN sed -i 's/\r$//' /entrypoint.sh

# 创建目录和设置环境变量
ENV CONFIG_PATH=/app/config/config.yaml
ENV FREQUENCY_WORDS_PATH=/app/config/frequency_words.txt

ENTRYPOINT ["/entrypoint.sh"]
```

#### entrypoint.sh 执行流程

```bash
#!/bin/bash

# 1. 验证配置文件
if [ ! -f "/app/config/config.yaml" ]; then
    echo "配置文件不存在: /app/config/config.yaml"
    exit 1

# 2. 根据 RUN_MODE 选择执行方式
case $RUN_MODE in
    cron)
        # 使用 supercronic 定时执行
        echo "0 * * * * python /app/main.py" | supercronic /dev/stdin
        ;;
    once)
        # 执行一次后退出
        python /app/main.py
        ;;
    *)
        # 默认：后台运行 HTTP 服务
        python /app/mcp_server/server.py --transport http
        ;;
esac
```

## 4. 关键设计决策

### 4.1 为什么分离 main.py 和 mcp_server/?

| 方面 | main.py | mcp_server/ |
|-----|--------|------------|
| 职责 | 爬虫 + 推送 | 数据查询 + 分析 |
| 触发方式 | 定时/手动执行 | 客户端按需调用 |
| I/O 模式 | 同步 I/O | 异步 I/O |
| 部署方式 | 后台服务 | 独立微服务 |
| 扩展性 | 添加新渠道难 | 添加新工具易 |

### 4.2 为什么使用文件系统而不是数据库？

✅ **优点**：
- 零依赖，30 秒快速部署
- 天然支持 GitHub Pages（静态文件托管）
- 数据清晰可见，便于调试
- 单机场景下足够

❌ **缺点**：
- 查询效率低（全表扫描）
- 无并发控制

### 4.3 为什么需要多个工具而不是单一 API？

✅ **好处**：
- 各工具独立职责，易于维护
- 工具可单独复用
- 易于添加新功能（新工具）
- 符合 MCP 工具标准

## 6. 总结

TrendRadar 的核心模块设计清晰，各司其职：

| 模块 | 职责 | 交互方式 |
|-----|------|---------|
| main.py | 爬虫 + 推送 | 主程序，定时/手动触发 |
| mcp_server/ | 数据查询 + AI 分析 | HTTP/STDIO，客户端按需调用 |
| config/ | 配置管理 | 外部化配置，无代码修改 |
| output/ | 数据持久化 | 文件系统存储 |
| docker/ | 容器化部署 | 支持多架构 |
