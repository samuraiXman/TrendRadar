# TrendRadar 数据流与处理分析

## 1. 典型请求处理流程

### 1.1 爬虫执行流程（完整版）

```
┌─────────────────────────────────────────────────────────────────┐
│                    爬虫执行流程 (完整版)                          │
└─────────────────────────────────────────────────────────────────┘

step 1: 初始化
  │
  ├─ 读取配置文件
  │  ├─ config/config.yaml
  │  ├─ config/frequency_words.txt
  │  └─ 环境变量覆盖
  │
  ├─ 初始化参数
  │  ├─ 爬虫开关: ENABLE_CRAWLER
  │  ├─ 通知开关: ENABLE_NOTIFICATION
  │  ├─ 推送模式: REPORT_MODE (daily/current/incremental)
  │  ├─ 监控平台: platforms (11+)
  │  └─ 权重配置: rank_weight=0.6, frequency_weight=0.3, ...
  │
  └─ 版本检查 (可选)
     └─ 对比本地版本与 GitHub 最新版本


step 2: 数据抓取
  │
  ├─ 调用 newsnow API
  │  ├─ 请求间隔: config.crawler.request_interval (1000ms)
  │  ├─ 代理设置: use_proxy + default_proxy (可选)
  │  ├─ 超时设置: 30s
  │  └─ 错误重试: 3 次
  │
  ├─ 获取数据结构
  │  └─ [{
  │       "title": "ChatGPT-5 正式发布",
  │       "desc": "...",
  │       "link": "https://...",
  │       "mobileLink": "https://...",
  │       "pic": "https://...",
  │       "commentCount": 100,
  │       "time": "2025-11-15 10:30:00",
  │       "channel": "baidu",
  │       "rank": 1
  │     }, ...]
  │
  └─ 处理多个平台数据
     └─ 聚合 11+ 个平台的数据


step 3: 数据规范化与存储
  │
  ├─ 数据清理
  │  ├─ 去除 HTML 标签
  │  ├─ 统一编码 (UTF-8)
  │  └─ 去除特殊字符
  │
  ├─ 去重检测
  │  ├─ 按标题 MD5 哈希检测
  │  ├─ 相似度匹配 (80% 相似视为重复)
  │  └─ 存储已见新闻 ID
  │
  ├─ 存储到文件
  │  ├─ 路径: output/2025年11月15日/txt/10时30分.txt
  │  ├─ 格式: 原始新闻 JSON + 元数据
  │  └─ 更新历史记录
  │     └─ output/.history/ (追踪新闻出现时间)
  │
  └─ 数据统计
     └─ 记录本次抓取的新闻数量、来源平台、排名分布等


step 4: 读取关键词配置
  │
  ├─ 解析 frequency_words.txt
  │  ├─ 按空行分组
  │  ├─ 识别语法
  │  │  ├─ 普通词 (or 关系)
  │  │  ├─ +必须词 (and 关系)
  │  │  ├─ !过滤词 (排除)
  │  │  └─ @数字 (数量限制)
  │  └─ 构建关键词分组表
  │
  └─ 返回结构
     └─ [
          {
            "keywords": ["AI", "ChatGPT", "人工智能"],
            "must_have": ["技术"],
            "exclude": ["广告"],
            "limit": 10
          },
          {
            "keywords": ["股市", "A股"],
            "must_have": ["涨跌"],
            "exclude": ["预测"],
            "limit": 5
          }
        ]


step 5: 关键词过滤
  │
  ├─ 遍历每条新闻
  │  └─ for news in all_news:
  │
  ├─ 对每个关键词分组过滤
  │  │
  │  ├─ 检查普通词匹配 (or)
  │  │  └─ if any(keyword in title for keyword in group.keywords)
  │  │
  │  ├─ 检查必须词 (and)
  │  │  └─ if all(must in title for must in group.must_have)
  │  │
  │  ├─ 检查过滤词 (排除)
  │  │  └─ if any(exclude in title for exclude in group.exclude):
  │  │       continue  # 跳过
  │  │
  │  └─ 匹配则添加到结果
  │     └─ matched_news[group_idx].append({
  │          "title": news.title,
  │          "platform": news.platform,
  │          "rank": news.rank,
  │          "timestamp": now,
  │          "platform_name": platform_map[news.platform]
  │        })
  │
  └─ 返回结构
     └─ {
          0: [news1, news2, ...],      # 第 1 组匹配的新闻
          1: [news3, news4, ...],      # 第 2 组匹配的新闻
          ...
        }


step 6: 权重计算
  │
  ├─ 读取历史数据
  │  ├─ 汇总所有历史文件中该新闻的出现记录
  │  ├─ 统计排名列表: [1, 2, 1, 3, 2, ...]
  │  └─ 计算出现次数: count = len(ranks)
  │
  ├─ 计算三个分量
  │  │
  │  ├─ 1. 排名权重 (占 60%)
  │  │    ├─ 公式: Σ(min(rank, 10) - 1) / count
  │  │    ├─ 范围: 0-10
  │  │    └─ 含义: 排名越前，分数越高
  │  │
  │  ├─ 2. 频次权重 (占 30%)
  │  │    ├─ 公式: min(count, 10) × 10
  │  │    ├─ 范围: 0-100
  │  │    └─ 含义: 出现次数越多，分数越高（最多10次计算）
  │  │
  │  └─ 3. 热度权重 (占 10%)
  │       ├─ 公式: (高排名次数 / 总次数) × 100
  │       ├─ 范围: 0-100
  │       └─ 含义: 排名靠前的比例越高，越热
  │
  ├─ 综合权重计算
  │  └─ total_weight = rank_score × 0.6 + freq_score × 0.3 + hot_score × 0.1
  │
  └─ 返回结构
     └─ {
          "title": "...",
          "weight": 42.5,
          "ranks": [1, 2, 1, 3],
          "count": 4,
          "rank_score": 6.5,
          "freq_score": 40,
          "hot_score": 75
        }


step 7: 数量限制应用 (@)
  │
  ├─ 读取全局配置
  │  └─ max_news_per_keyword = config.report.max_news_per_keyword
  │
  ├─ 检查单个关键词配置
  │  └─ if group 有 @N，则 limit = N
  │     else limit = max_news_per_keyword
  │
  └─ 截断列表
     └─ matched_news = matched_news[:limit]


step 8: 排序
  │
  ├─ 检查排序优先级配置
  │  └─ sort_by_position_first = config.report.sort_by_position_first
  │
  ├─ 情况 1: sort_by_position_first = false (默认)
  │  ├─ 按热度排序
  │  └─ matched_news.sort(key=lambda x: -x['weight'])
  │
  ├─ 情况 2: sort_by_position_first = true
  │  ├─ 按关键词配置位置排序
  │  └─ 保持 frequency_words.txt 中的顺序
  │
  └─ 返回
     └─ 已排序的 matched_news


step 9: 选择推送模式
  │
  ├─ 读取 report.mode 配置
  │
  ├─ 模式 A: daily (当日汇总)
  │  ├─ 读取今天的所有历史文件
  │  ├─ 合并所有已匹配的新闻
  │  ├─ 去除重复标题
  │  └─ 按时间排序
  │
  ├─ 模式 B: current (当前榜单)
  │  ├─ 读取最新时刻的新闻数据
  │  ├─ 对最新数据进行关键词过滤
  │  └─ 返回当前时刻的新闻集合
  │
  └─ 模式 C: incremental (增量监控)
     ├─ 比较本次数据与上次推送数据
     ├─ 计算差集 (本次 - 上次)
     └─ 仅返回新增的新闻


step 10: 检查推送时间窗口 (可选)
  │
  ├─ 如果 push_window.enabled = false
  │  └─ 跳过此步
  │
  ├─ 如果 push_window.enabled = true
  │  ├─ 获取当前时间 (北京时间)
  │  ├─ 检查是否在 [start, end] 时间范围内
  │  │  └─ if not (start <= now <= end):
  │  │       return "在非推送时间，跳过"
  │  │
  │  ├─ 检查 once_per_day 配置
  │  │  ├─ if once_per_day = true:
  │  │  │   └─ 检查是否已在今天推送过
  │  │  │      └─ if today_already_pushed:
  │  │  │           return "今天已推送，跳过"
  │  │  │
  │  │  └─ if once_per_day = false:
  │  │      └─ 允许窗口内每次都推送
  │  │
  │  └─ 记录本次推送时间戳


step 11: 构建推送消息
  │
  ├─ 渲染模板
  │  ├─ 标题: "📊 热点词汇统计"
  │  ├─ 分组标题: "🔥 [1/3] AI ChatGPT : 2 条"
  │  ├─ 新闻条目: "1. [平台] 🆕 标题 [排名] - 时间 (次数)"
  │  └─ 新增区域: "🆕 本次新增热点新闻"
  │
  ├─ 格式化
  │  ├─ 平台特定格式 (Markdown/纯文本)
  │  ├─ 符号和表情符号
  │  └─ 时间戳
  │
  └─ 返回消息体


step 12: 消息分批处理
  │
  ├─ 检查消息大小
  │  └─ message_size = len(message_text)
  │
  ├─ 比较限制大小
  │  └─ limit_size = config.notification.{platform}_batch_size
  │
  ├─ 情况 1: message_size <= limit_size
  │  └─ 直接发送
  │
  └─ 情况 2: message_size > limit_size
     ├─ 按分割线 ("━━━") 分割
     ├─ 每个分段控制在 limit_size 以内
     ├─ 添加批次标记 "[第 X/Y 批次]"
     └─ 返回消息列表


step 13: 多渠道推送
  │
  ├─ 并行检查所有配置的通知渠道
  │  │
  │  ├─ 企业微信 (wework_webhook_url)
  │  │  ├─ 构建 Markdown/Text 格式消息
  │  │  ├─ POST 到 https://qyapi.weixin.qq.com/cgi-bin/webhook/send
  │  │  └─ 分批推送
  │  │
  │  ├─ 飞书 (feishu_webhook_url)
  │  │  ├─ 构建飞书消息格式
  │  │  ├─ POST 到 Webhook URL
  │  │  └─ 分批推送
  │  │
  │  ├─ 钉钉 (dingtalk_webhook_url)
  │  │  ├─ 构建钉钉 Markdown 格式
  │  │  ├─ 添加安全关键词 ("热点")
  │  │  └─ 分批推送
  │  │
  │  ├─ Telegram (telegram_bot_token)
  │  │  ├─ 调用 Bot API
  │  │  ├─ 使用 HTML 格式
  │  │  └─ 分批推送
  │  │
  │  ├─ 邮件 (email_from, email_password, email_to)
  │  │  ├─ 识别邮箱服务商 (自动识别 SMTP)
  │  │  ├─ 建立 SMTP 连接 (SSL/TLS)
  │  │  ├─ 构建 HTML 邮件体
  │  │  └─ 发送给多个收件人
  │  │
  │  ├─ ntfy (ntfy_server_url, ntfy_topic)
  │  │  ├─ POST 到 {ntfy_server_url}/{ntfy_topic}
  │  │  └─ 纯文本格式
  │  │
  │  ├─ Bark (bark_url)
  │  │  ├─ POST 推送 URL
  │  │  ├─ 纯文本格式
  │  │  └─ 分批推送
  │  │
  │  └─ Slack (slack_webhook_url)
  │     ├─ POST 到 Incoming Webhook
  │     ├─ 构建 mrkdwn 格式
  │     └─ 分批推送
  │
  ├─ 错误处理
  │  ├─ 重试机制: 最多 3 次
  │  ├─ 指数退避: 1s, 2s, 4s
  │  └─ 记录错误日志
  │
  └─ 返回推送结果
     └─ {
          "wework": {"success": true, "time": "10:30:15"},
          "feishu": {"success": true, "time": "10:30:16"},
          "dingtalk": {"success": false, "error": "Network timeout"},
          ...
        }


step 14: 清理与统计
  │
  ├─ 更新推送记录
  │  └─ 记录本次推送的时间戳 (用于 once_per_day)
  │
  ├─ 生成统计日志
  │  ├─ 本次抓取: X 条新闻
  │  ├─ 匹配: Y 条
  │  ├─ 推送渠道: Z 个成功
  │  └─ 执行耗时: T ms
  │
  └─ 可选: 生成 HTML 报告
     └─ output/html/index.html (用于 GitHub Pages)


end: 爬虫执行完毕
```

### 1.2 数据处理时间复杂度分析

| 步骤 | 数据规模 | 时间复杂度 | 实际耗时 |
|-----|---------|-----------|---------|
| 1. 初始化 | - | O(1) | ~100ms |
| 2. 数据抓取 | 11 平台 × 50 条 | O(p × n) | ~5-10s (网络 I/O) |
| 3. 数据规范化 | ~550 条 | O(n × m) | ~500ms |
| 4. 读取关键词 | - | O(1) | ~10ms |
| 5. 关键词过滤 | 550 条 × 100 词 | O(n × k) | ~1-2s |
| 6. 权重计算 | ~200 条 | O(n × log n) | ~500ms |
| 7. 排序 | ~200 条 | O(n × log n) | ~100ms |
| 8. 推送模式 | ~200 条 | O(n) | ~100ms |
| 9. 时间窗口 | - | O(1) | ~10ms |
| 10. 构建消息 | ~200 条 | O(n) | ~200ms |
| 11. 消息分批 | ~200 条 | O(n) | ~100ms |
| 12. 多渠道推送 | 8 渠道 | O(p) (网络 I/O) | ~3-10s |
| **总计** | - | - | **11-24s** |

**瓶颈识别**：
- 🔴 **数据抓取** (5-10s)：网络 I/O，难以优化
- 🔴 **多渠道推送** (3-10s)：网络 I/O，可改进为并行
- 🟡 **关键词过滤** (1-2s)：O(n × k)，可优化为哈希表
- 🟢 **其他步骤** (<500ms)：可忽略

## 2. 数据在系统中的流动路径

### 2.1 完整数据流动图

```
┌─────────────────────────────────────────────────────────────────┐
│                      数据流动完整图                              │
└─────────────────────────────────────────────────────────────────┘

外部数据源 (newsnow API)
    │ HTTP GET
    ↓
    ┌──────────────────────────────────────────────────┐
    │ 原始新闻数据 (550 条/次)                          │
    │ ├─ title: "ChatGPT-5 正式发布"                   │
    │ ├─ platform: "baidu"                            │
    │ ├─ rank: 1                                      │
    │ ├─ time: 1721040600                            │
    │ └─ link: "https://..."                          │
    └──────────────────────────────────────────────────┘
    │ 处理
    ↓
    ┌──────────────────────────────────────────────────┐
    │ 数据规范化 (UTF-8, 去 HTML)                      │
    │ 去重 (按标题 MD5)                               │
    │ 550 → 480 条 (20 条重复)                        │
    └──────────────────────────────────────────────────┘
    │ 存储
    ↓
    ┌──────────────────────────────────────────────────┐
    │ 文件系统存储                                      │
    │ output/2025年11月15日/txt/10时30分.txt           │
    │ 480 条新闻 (JSON 格式)                           │
    │ + 元数据 (抓取时间、平台统计等)                  │
    └──────────────────────────────────────────────────┘
    │
    ├─────→ 查询 1: 读取最新新闻
    │        DataService.get_latest_news()
    │        ↓
    │        MCP 客户端 (Claude / Cursor)
    │
    ├─────→ 查询 2: 关键词搜索
    │        DataService.search_news_by_keyword()
    │        ↓
    │        MCP 客户端
    │
    └─────→ 推送流程:
           │
           ├─ 读取关键词配置
           │  └─ frequency_words.txt
           │
           ├─ 关键词过滤
           │  ├─ 普通词匹配 (OR)
           │  ├─ 必须词验证 (AND)
           │  ├─ 过滤词排除
           │  └─ 480 → 150 条 (匹配)
           │
           ├─ 权重计算
           │  ├─ 排名权重 + 频次权重 + 热度权重
           │  └─ 150 条 → {title, weight, rank_score, ...}
           │
           ├─ 排序
           │  ├─ 按 weight 降序
           │  └─ 150 条 → [news1, news2, ..., news150]
           │
           ├─ 推送模式选择
           │  ├─ daily: 150 条
           │  ├─ current: 当前时刻的新闻
           │  └─ incremental: 新增新闻
           │
           ├─ 消息构建与分批
           │  ├─ 格式化为 Markdown
           │  ├─ 按消息大小分批
           │  └─ 150 条 → 3 个消息 (4KB each)
           │
           └─ 多渠道推送
              ├─ Webhook POST (企业微信/飞书/钉钉/ntfy/Slack)
              ├─ HTTP GET/POST (Telegram/Bark)
              ├─ SMTP (邮件)
              └─ 3 消息 × 8 渠道 → 用户设备

最终：用户手机/邮箱接收到个性化的热点新闻推送
```

### 2.3 关键词过滤详细流程

```
关键词过滤流程
│
输入：480 条新闻 + 关键词配置
│
frequency_words.txt:
  │
  ├─ 第1组: AI ChatGPT +技术 !广告 @10
  │   │
  │   ├─ AI, ChatGPT 中的任意一个 (OR)
  │   ├─ 必须包含 "技术" (AND)
  │   ├─ 不能包含 "广告" (NOT)
  │   └─ 最多显示 10 条
  │
  └─ 第2组: 股市 A股 !预测 @5
      │
      ├─ 股市, A股 中的任意一个 (OR)
      ├─ 不能包含 "预测" (NOT)
      └─ 最多显示 5 条
│
对每条新闻进行过滤:
│
for news in news_list:
  │
  for group in groups:
    │
    ├─ 检查普通词
    │  └─ if any(keyword in news.title for keyword in group.keywords):
    │       next_check = True
    │     else:
    │       continue  # 不匹配，跳过该分组
    │
    ├─ 检查必须词
    │  └─ if next_check and all(must in news.title for must in group.must_haves):
    │       next_check = True
    │     else:
    │       continue
    │
    ├─ 检查过滤词
    │  └─ if next_check and any(exclude in news.title for exclude in group.excludes):
    │       continue  # 被排除
    │
    └─ 匹配成功
       └─ matched[group_idx].append(news)
│
└─ 输出：按分组组织的匹配新闻
   ├─ 第1组：[news1, news2, ..., news10]  # 10 条
   └─ 第2组：[news11, news12, ..., news15]  # 5 条
```

## 3. 性能瓶颈识别

### 3.1 关键性能瓶颈

#### 🔴 瓶颈 1: 网络 I/O (最严重)

```
问题：数据抓取 + 推送都涉及网络请求
├─ 数据抓取: newsnow API (5-10s) *1
├─ 推送: 8 个渠道，串行推送 (3-10s) *1
└─ 总耗时: 8-20s (其中 60% 是网络等待)

当前实现：
└─ requests 同步 I/O (阻塞)

改进方案：
├─ 使用 aiohttp 异步并发
├─ 连接池复用
└─ 并行推送 8 个渠道 (理论 8x 加速)
```

#### 🔴 瓶颈 2: 关键词过滤算法 (中等)

```
问题：O(n × k) 复杂度，n=480条新闻，k=100个关键词
├─ 480 × 100 = 48,000 次字符串搜索
├─ 每次搜索 O(m) (title 长度)
└─ 总计: O(n × k × m) = 48,000 × 50 = 2,400,000 次字符比较

当前实现：
└─ 简单的 `in` 操作 (Python 串行)

改进方案：
├─ 使用 Aho-Corasick 算法 O(n + k)
├─ 预编译正则表达式
└─ 多线程并行处理
```

#### 🟡 瓶颈 3: 文件 I/O (轻度)

```
问题：每次爬虫需要读取多个历史文件
├─ 读取今天所有历史数据 (daily 模式)
├─ 文件数: ~24 个 (每小时一个)
└─ 每个文件: ~50KB

当前实现：
└─ 同步文件读取

改进方案：
├─ 内存缓存 (已实现 CacheService)
├─ 预加载热数据
└─ 数据库索引 (SQLite)
```

#### 🟢 瓶颈 4: 权重计算 (轻度)

```
问题：需要读取历史数据计算权重
├─ 每条新闻: 多次查询历史
├─ 效率: O(n × log d) (d=天数)
└─ 总计: 200 条新闻 × log(30天) ≈ 1000 次查询

当前实现：
└─ 遍历所有文件查找

改进方案：
├─ 预计算索引
├─ 缓存排名历史
└─ 数据库查询优化
```

```
┌───────────────────────────────────────────────────┐
│              单点故障风险识别                      │

🔴 高风险:

1. newsnow API 故障

   ├─ 概率: 中等 (第三方服务)

🟢 低风险:

5. 内存溢出
   ├─ 影响: 进程崩溃
   ├─ 概率: 低 (数据量小)
   ├─ 改进:

      ├─ 分批读取
      └─ 内存监控
```

## 4. 数据一致性与完整性

### 4.1 数据去重机制

```
去重流程:

1. 生成哈希值
   ├─ hash(title) = MD5(title.lower().strip())
   └─ 存储在 .seen_hashes

2. 检查是否已见
   ├─ if hash in .seen_hashes:
   │    skip_this_news()
   └─ else:
       add_to_seen_hashes()

3. 去重后处理
   ├─ 480 条原始 → 460 条去重后
   ├─ 20 条重复 (同一时刻不同平台)
   └─ 记录去重统计

问题：
├─ 相似但不完全相同的新闻无法识别 (如标题略微不同)
├─ 历史数据较长时间会占用大量存储
└─ 去重粒度可能过粗 (不考虑平台信息)

改进:
├─ 余弦相似度计算 (Jaccard/Cosine)
├─ 定期清理过期哈希
└─ 按平台+标题复合去重
```

### 4.2 数据完整性验证

```
数据完整性检查:

1. 文件存在性检查
   ├─ output/YYYY年MM月DD日/txt/ 必须存在
   └─ 若不存在则创建

2. 数据格式验证
   ├─ JSON 格式检查
   ├─ 必需字段: title, platform, rank, timestamp
   └─ 类型检查: rank 必须是整数

3. 数据范围验证
   ├─ rank: 1-100 范围
   ├─ timestamp: 合理时间戳
   └─ title 长度: 1-500 字符

4. 数据一致性检查
   ├─ 同一新闻在多个平台的排名是否合理
   ├─ 推送记录是否与实际推送一致
   └─ 缓存数据是否与文件同步

问题：
├─ 无统一的数据验证框架
├─ 错误数据可能导致推送失败
└─ 难以追踪数据流动中的问题

改进:
├─ JSON Schema 定义
├─ 数据校验管道
└─ 审计日志记录
```

## 5. 推送可靠性分析

### 5.1 推送失败处理

```
推送流程与容错:

for each_batch in batches:
  for each_channel in [wework, feishu, dingtalk, ...]:
    
    retry_count = 0
    while retry_count < 3:
      try:
        response = send_webhook(batch, channel)
        if response.status == 200:
          success()
          break
      except Exception as e:
        retry_count += 1
        if retry_count < 3:
          wait(2 ^ retry_count)  # 1s, 2s, 4s
        else:
          failed(e)  # 最终失败
          log_error()  # 记录错误

问题：
├─ 无消息持久化 (推送失败后无法恢复)
├─ 无推送状态追踪 (用户不知道是否推送成功)
├─ 无死信队列 (重试 3 次后消息丢失)
└─ 无补偿机制 (错过的推送无法补送)

改进方案：
├─ Redis Queue / RabbitMQ 持久化
├─ 推送状态数据库记录
├─ 死信队列 + 人工介入
└─ 用户推送状态查询接口
```

### 5.2 推送延迟分析

```
推送延迟组成:

爬虫执行 (0-60s)
  │
  ├─ API 抓取: 5-10s
  ├─ 数据处理: 1-2s
  └─ 关键词过滤: 1-2s
  │
  └─ 总计: 7-14s
  │
  └─ [消息构建] (0.2s)
  │
  └─ [多渠道推送] (3-10s)
      ├─ 企业微信: 1s (可能延迟 5s+)
      ├─ 飞书: 0.5s
      ├─ 钉钉: 1-2s
      ├─ Telegram: 2-3s
      ├─ 邮件: 5-10s (SMTP)
      └─ ... (并行推送能加速)
  │
└─ [用户接收] (网络延迟 + 手机)
    └─ 总延迟: 15-40s (现状)
    └─ 优化后: 5-15s (使用并发)

关键：大部分延迟来自网络 I/O，串行推送浪费时间
```

## 6. 总结与改进建议

### 性能优化优先级

| 优化项 | 当前 | 目标 | 难度 | 收益 |
|--------|------|------|------|------|
| 异步 I/O | 串行 | 并行 | 中 | 🔴 高 (8x 加速) |
| 算法优化 | O(n×k) | O(n+k) | 中 | 🟡 中 (3x 加速) |
| 缓存策略 | 内存 | 多层缓存 | 低 | 🟢 低 (2x 加速) |
| 数据库集成 | 文件系统 | SQLite | 高 | 🟡 中 (查询加速) |

### 可靠性改进优先级

| 改进项 | 重要度 | 难度 | 收益 |
|-------|--------|------|------|
| 消息队列 | 🔴 高 | 高 | 极高 |
| 多数据源 | 🔴 高 | 中 | 极高 |
| 配置验证 | 🟡 中 | 低 | 中 |
| 推送确认 | 🟡 中 | 中 | 中 |
| 错误告警 | 🟢 低 | 低 | 低 |
